TLS

记录层和握手建立在可靠字节流上，也就是 TCP。两端先谈妥是谁、用哪套密钥，再保护这条字节流。

握手在谈什么

握手要定三件事：协议版本、随后用来保护记录的参数，以及对面的身份。身份靠证书。诊断连接常见两边都有证书，诊断仪认车，车也认这台诊断仪。只验一边的做法也有，车上的诊断和刷写更常见的是互相验。

TLS 1.3（RFC 8446）一轮新的握手，报文按这个次序走。除了开头两条，后面的都已经包在加密的记录里：

报文谁发谈成什么
ClientHello客户端支持的版本、密钥交换、以及自己的随机数
ServerHello服务端选定的参数和自己的随机数
EncryptedExtensions服务端其余扩展，已经加密
Certificate要被验的一方证书链。互相认证时两边都送
CertificateVerify证书的持有者用私钥对握手内容签名，证明拿着这张证书的私钥
Finished两边对整个握手做一次校验，对上之后应用数据才能走

1.3 里各方都要实现的那套保护是 TLS_AES_128_GCM_SHA256。还有哪些套件可以出现，由部署决定。算法和密钥放在哪，看 AI Fortress Auto 的 HSM 说明，这页不写计算过程。

车上的诊断链路也有仍按 TLS 1.2 来做的。1.2 多一轮明文的密钥交换和 ChangeCipherSpec，总图不把两个版本分成两格。DoIP 遇到路由激活被拒绝、原因是要求加密时，改连 TCP 3496 再握一次，见 DoIP。

会话可以恢复，少走一轮证书。1.3 还有 0-RTT 的早数据，这段数据有被重放的可能。诊断和刷写不靠它来送第一条命令。

警报

握手或记录对不上时，送一条警报然后把连接拆掉。常见的有：

警报发生在什么时候
close_notify一边正常说结束，不是出错
handshake_failure版本或参数对不拢
certificate_unknown / bad_certificate证书链不被信任，或证书本身有问题
bad_record_mac记录的校验对不上，密文被改过或密钥不一致
unexpected_message这个时候不该出现这种报文

在哪一层

总图把记录层画在表示层，握手画在会话层，都夹在应用和 TCP 之间。帧上不另加以太网首部。SOME/IP、DDS、Zenoh 默认 UDP，要先把传输改成 TCP 才能勾。gPTP 没有字节流，加不上。

握手会话层

线上，握手报文装在记录里送，不是记录旁边再加一个以太网首部。两格是总图上的分层。

报文

记录头带类型、遗留的版本字段和长度，受保护的内容跟在后面。1.3 里真正的内容类型放在加密之后的明文尾部，头上的类型常常只写成“应用数据”，用来不把握手和警报暴露在外面。

类型记录头
版本记录头里的遗留字段
长度后面有多长
受保护的内容握手、警报或应用数据

应用数据是一整条字节流。DoIP 的头和 UDS 都在这流里面，靠 DoIP 自己的长度字段切开，TLS 不认识服务号。SOME/IP 若走 TCP 再套 TLS，同样靠 SOME/IP 的长度字段切开。

不做什么

  • 不保护 UDP。没有可靠字节流，就套不上这里画的 TLS。DTLS 走数据报，总图不画。
  • 不是逐跳的。交换机看不见里面，保护停在这条 TCP 的两端。逐跳是 MACsec。
  • 不是 DDS-Security。DDS 的保护做在 RTPS 上，不靠这条字节流。
  • 不是 IPsec。IPsec 加在 IP 和传输头之间，UDP 和 TCP 都能用。
  • 不是 SecOC。SecOC 给每一条 PDU 单独做 MAC。TLS 保护的是整条字节流，不给某一条 SOME/IP 单独签名。
