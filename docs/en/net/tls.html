TLS

The record layer and the handshake sit on a reliable byte stream, which means TCP. The two ends agree who they are and which keys to use, and then protect that byte stream.

What the handshake agrees

The handshake settles three things: the protocol version, the parameters that will protect the records, and the identity of the other side. Identity comes from a certificate. A diagnostic connection commonly has a certificate on both sides: the tester checks the vehicle, and the vehicle checks the tester. Checking only one side also exists. Diagnostics and flashing in a vehicle more often check both.

In TLS 1.3 (RFC 8446), when the key share is accepted immediately, a new handshake follows this order. If the server does not accept the client’s key share, it first returns HelloRetryRequest and the client sends ClientHello again. Blue to the right is the client. Orange to the left is the server. The first two messages are still plaintext. From EncryptedExtensions on, the handshake messages are inside an encrypted record. The drawing below is the mutual authentication common in vehicle diagnostics: the server asks the client for a certificate with CertificateRequest. When only one side is checked, that message is not sent, and the client sends no certificate.

The protection every TLS 1.3 implementation must provide is TLS_AES_128_GCM_SHA256. Which other suites may appear is a deployment choice. Where the algorithms and keys live is in the HSM note of AI Fortress Auto. This page does not describe the computation.

Some diagnostic links in vehicles are still done as TLS 1.2. Version 1.2 adds another cleartext key exchange and ChangeCipherSpec. The overview does not split the two versions into two cells. When DoIP rejects routing activation because encryption is required, connect to TCP 3496 and handshake again. See DoIP.

A session can be resumed, and that skips a round of certificates. TLS 1.3 also has 0-RTT early data, which can be replayed. Diagnostics and flashing do not use it to send the first command.

Alerts

When the handshake or a record does not check out, an alert is sent and the connection is torn down. Common ones:

AlertWhen it happens
close_notifyOne side says it is finished. This is not an error
handshake_failureThe version or the parameters cannot be agreed
certificate_unknown / bad_certificateThe certificate chain is not trusted, or the certificate itself is wrong
bad_record_macThe record check fails. The ciphertext was altered, or the keys do not match
unexpected_messageThis message does not belong at this point

Where it sits

The overview draws the record layer at the presentation layer and the handshake at the session layer, both between the application and TCP. The Ethernet frame gains no extra header. SOME/IP, DDS, and Zenoh default to UDP and must be switched to TCP before TLS can be selected. gPTP has no byte stream, so TLS cannot be added.

On the wire, handshake messages travel inside records. They are not an extra Ethernet header beside the record. The two cells are the layers on the overview.

Packet

The record header carries a type, a legacy version field, and a length. The protected content follows. In TLS 1.3 the real content type sits at the end of the plaintext, after decryption. The type in the header is often written only as application data, so the handshake and alerts are not exposed outside.

TypeRecord header
VersionThe legacy field in the record header
LengthHow long the rest is
Protected contentHandshake, alert, or application data

Application data is one byte stream. The DoIP header and UDS are both inside that stream and are cut apart by DoIP’s own length field. TLS does not know service IDs. If SOME/IP runs on TCP and then TLS, it is likewise cut apart by the SOME/IP length field.

What it does not do

  • It does not protect UDP. Without a reliable byte stream, the TLS drawn here does not fit. DTLS runs on datagrams and is not drawn on the overview.
  • It is not hop by hop. A switch cannot see inside. Protection stops at the two ends of this TCP connection. Hop by hop is MACsec.
  • It is not DDS-Security. DDS protection is done on RTPS and does not use this byte stream.
  • It is not IPsec. IPsec sits between the IP header and the transport header, and works for both UDP and TCP.
  • It is not SecOC. SecOC puts a MAC on each PDU. TLS protects the whole byte stream and does not sign one SOME/IP message on its own.
