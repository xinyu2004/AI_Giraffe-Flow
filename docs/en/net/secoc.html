SecOC

A MAC and a freshness value are added on an application PDU, to recognize who sent it and whether it was just sent. The payload is not encrypted.

Which PDU is protected

This is AUTOSAR Secure Onboard Communication. The protected part is the authentic PDU. After a freshness value and a truncated authenticator are added, it is the secured PDU. On the overview that PDU is SOME/IP. Freshness is a counter or a time, so an old PDU cannot be replayed unchanged. The MAC is computed from the freshness, a data ID, and the PDU contents. The receiver recomputes it with the same key and accepts the PDU only when the values match.

The data ID separates “this PDU” from “another PDU that looks like it”. It takes part in the computation and does not have to appear in full on the wire. After truncation, the wire shows only part of the freshness and part of the MAC. The lengths are configuration: how many freshness bits, and how many authenticator bits. Both sides must use the same lengths.

The steps that wrap and unwrap a PDU are in section 3 of AI Fortress Auto. Which algorithm is used, and where the key is kept, are in that HSM note. This page stops at the two extra fields on the PDU, and at how the receiver keeps up with freshness.

How freshness stays in step

Each time the sender transmits, it increments the full freshness (or takes the current time), truncates it as configured, and sends that with the truncated MAC. The receiver holds the full freshness of the last PDU it accepted. It tries to build a candidate full value from the truncated value on the wire and the high bits it remembers, then computes the MAC.

Truncation is ambiguous, so the receiver does not try only one number. The acceptance window lets it try several fresher values. If one of them makes the MAC match, the PDU is accepted and the remembered freshness moves forward. If none match, the PDU is discarded. A window that is too wide makes an old PDU easier to accept. A window that is too narrow loses the sequence after a few dropped PDUs. The width is configuration, not a fixed constant in the protocol.

A failed build can be retried a configured number of times and then given up. Verification failure has a count as well. After overflow the freshness wraps. Both sides must understand that wrap the same way, or a new PDU will be treated as a replay.

Where it sits

It stays at the application layer, on the SOME/IP PDU. On the overview only SOME/IP can select it. It adds no Ethernet header and does not change UDP or TCP. A switch or a router cannot see this MAC. They only forward the original UDP or TCP packet.

Packet

A secured PDU adds two fields outside the authentic PDU. Which end of the PDU those fields occupy is a configured position. This page does not draw one truncation length as the only layout.

Authentic PDUThe original application data
FreshnessA truncated counter or time
MACTruncated. The length is configured

The MAC computation also includes the data ID and the full freshness. The part that is not on the wire is filled in from what both sides agreed in advance and from the state the receiver remembers.

What it does not do

  • It does not encrypt the payload. Confidentiality is not what this MAC is for.
  • It is not E2E. The E2E counter and CRC have no key, and they do not identify who signed.
  • It does not protect the whole Ethernet frame, and it does not protect the whole IP packet. The frame is MACsec. IP is IPsec. The byte stream is TLS.
  • The overview does not put it on DDS, DoIP, Zenoh, or gPTP. DDS authentication is inside DDS-Security.
