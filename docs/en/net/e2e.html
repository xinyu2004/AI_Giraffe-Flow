AutoEth

E2E

A counter, a length, a data ID, and a CRC are added on an application PDU, to detect loss, repetition, a wrong order, a different PDU inserted in the stream, and bit errors.

What it can detect

This is AUTOSAR end-to-end protection. There is no key. Each time the sender transmits, it increments a counter, wrapping back to 0 at the end, and computes a CRC over the header and the user data. The receiver checks the CRC first, then checks that the counter follows the previous one. The data ID separates this data from other data on the network, so someone else’s PDU is not accepted as this one.

FaultHow it shows up
RepetitionThe counter did not move forward
Loss, timeoutThe counter jumped, or no new counter arrived in time
Wrong orderThe counter is not the expected next value
Another PDU inserted, or the wrong addressThe data ID is wrong, and the CRC does not match either
Bits were changedThe CRC

This does not identify who signed. To identify the sender, use the MAC in SecOC. Both can be added on the same PDU. Each is computed on its own.

Profiles

A profile decides how wide the fields are and where they sit. Short PDUs often use Profile 1: CRC-8, a 4-bit counter, and several ways for the data ID to enter the CRC (both bytes, alternating with the counter’s parity, or only the low byte). On Ethernet and SOME/IP, Profile 4 is the more common one. Its header is a fixed 12 bytes and can cover variable-length data.

The Profile 4 header

Fields are big-endian. The specification sets the start at offset 0. The whole header can be placed inside the protected data at a configured offset. In SOME/IP it is usually inside the payload and does not occupy the SOME/IP header itself.

Length16 bits, offset 0
Counter16 bits, offset 2
Data ID32 bits, offset 4
CRC32 bits, offset 8

The length counts both the E2E header and the user data, so a variable-length payload can still be checked. The CRC polynomial is 0xF4ACFB13 (CRC32P4 in CRC libraries). It is not the polynomial of the Ethernet FCS, or of CAN, or of FlexRay, so a frame check cannot stand in for it. The computation covers the E2E header except the CRC itself, plus the user data.

Wider profiles also exist, for example a 64-bit CRC and a 32-bit counter, for especially long data. A short profile and Profile 4 should not be mixed on the same stretch of one PDU. The profile, the offset, and the data ID chosen by the two sides must be the same configuration.

How the receiver decides

A single check and the state over a stretch of time are two layers. The single check looks at this PDU. The state machine looks at how many were good and how many were bad in a recent window, so one error does not mark the signal invalid, and one lucky success does not mark a bad channel good.

This PDUMeaning
OKThe CRC matches, and the counter is the expected next value
OK, some lostThe CRC matches, and the counter jumped forward, but it is still inside the allowed window
RepeatedThe counter did not advance
Wrong sequenceThe counter jumped past the window, or moved backward
ErrorThe CRC does not match, or the length or data ID does not
No new dataNo new PDU was on the wire at this read

The state machine has four states: no data yet, init, valid, and invalid. The counts of correct and incorrect checks in the window decide which state it stays in. The thresholds come from configuration. What the application reads is this state, which is not necessarily the raw check of the PDU just received.

Where it sits

It stays at the application layer, on the SOME/IP PDU. On the overview only SOME/IP can select it. The frame gains no header.

What it does not do

  • There is no key, so the sender cannot be identified.
  • It is not the end-to-end delay in IEEE 802.1AS. That E2E is about the timing path. The E2E on this page is the counter and CRC on a PDU.
  • It does not link to AI Fortress Auto. There is no key here, and no algorithm section.
  • It is not added on DDS. DDS reliability is written in QoS, and the acknowledgement is the RTPS ACKNACK. DDS does not use this AUTOSAR profile.
  • A matching CRC only says the bits did not change and the ID matches. It does not prove the PDU came from an ECU that holds a particular key.
